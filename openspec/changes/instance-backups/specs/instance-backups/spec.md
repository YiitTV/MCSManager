# Spec Delta

## Purpose

Provides scheduled and on-demand backups of selected parts of an instance working directory, streamed into archives, stored on local disk and optionally on S3-compatible storage or Google Drive, with per-plan retention, restore, strict role permissions, secret protection, and success/failure events.

## ADDED Requirements

### Requirement: Destinations are administrator-managed
Backup destinations of type `local`, `s3`, and `gdrive` SHALL be created, updated, tested, listed, and deleted only by administrators. Regular users SHALL NOT read destination configuration or secrets.

#### Scenario: Administrator creates an S3 destination
- **WHEN** an administrator saves an S3 destination with endpoint, region, bucket, access key, secret key, optional path prefix, and path-style toggle
- **THEN** the destination is stored and its secret key is stored encrypted

#### Scenario: Regular user cannot access destinations
- **WHEN** a regular user lists, reads, creates, updates, tests, or deletes a destination
- **THEN** the panel responds with a forbidden error and changes nothing

#### Scenario: Deleting a destination in use
- **WHEN** an administrator deletes a destination referenced by an existing plan
- **THEN** the request is rejected with a conflict error naming the plan count

#### Scenario: Destination shape
- **WHEN** an administrator saves a destination
- **THEN** it has a unique id, a type, a name of 1 to 40 characters, non-secret configuration, and secrets; a `local` destination has an absolute directory and a maximum total size, and a default `local` destination exists

#### Scenario: Users see names only
- **WHEN** a regular user lists plans or backups of an assigned instance
- **THEN** destinations appear only as name and type

### Requirement: Secrets are never returned or logged
The panel SHALL encrypt destination secrets (S3 secret key, Google client secret, refresh token, service account private key) at rest, SHALL return the masked marker `__MCSM_SECRET_DATA__` in place of any non-empty secret in every API response, and SHALL keep the stored secret when an update sends the masked marker. Secrets SHALL NOT appear in logs, operation logs, error messages, notification events, or backup records.

#### Scenario: Masked on read
- **WHEN** an administrator lists destinations that have secrets
- **THEN** every secret field is the masked marker or empty, and no real secret value is present in the response

#### Scenario: Masked value keeps the stored secret
- **WHEN** an administrator updates a destination name and sends the masked marker for the secret key
- **THEN** the stored secret key is unchanged

#### Scenario: Errors do not leak secrets
- **WHEN** an upload fails because of an authentication error
- **THEN** the recorded error text contains no access key, secret key, token, or authorization header value

### Requirement: S3-compatible destination
The daemon SHALL upload to an S3-compatible endpoint using AWS Signature Version 4 and multipart upload, holding at most one part in memory, and SHALL abort the multipart upload on failure. Object keys SHALL be generated by the daemon and SHALL NOT contain client-supplied path text.

#### Scenario: Streamed multipart upload
- **WHEN** a 2 GiB archive is uploaded
- **THEN** the upload completes using multipart parts and the daemon never holds more than one part in memory

#### Scenario: Failed upload aborts the multipart
- **WHEN** a part upload fails after retries
- **THEN** the multipart upload is aborted and the destination result is recorded as failed

#### Scenario: Path-style endpoint
- **WHEN** the destination has path-style enabled
- **THEN** requests use `https://<endpoint>/<bucket>/<key>` addressing

#### Scenario: Part sizes
- **WHEN** an archive is uploaded
- **THEN** parts are 8 MiB, or 16 MiB when 8 MiB parts would exceed 10000 parts

#### Scenario: Generated keys
- **WHEN** an object key is built
- **THEN** it consists of the optional prefix, instance uuid, plan id, backup id, and a fixed extension

### Requirement: S3 endpoint safety
The panel SHALL validate an S3 endpoint as an `https` URL of at most 255 characters with no credentials, query, or fragment. The daemon SHALL resolve the hostname, pin the validated address for the connection, and reject private, loopback, and link-local addresses unless the administrator enabled the destination's allow-private-network setting.

#### Scenario: Private endpoint refused by default
- **WHEN** an S3 destination endpoint resolves to a private address and the private-network setting is off
- **THEN** testing or uploading to it fails with an endpoint-not-allowed error and no request is sent to the address

#### Scenario: Credentials in the URL are refused
- **WHEN** an administrator saves an endpoint containing `user:pass@`
- **THEN** the save is rejected with a validation error

#### Scenario: DNS rebinding
- **WHEN** a hostname validates as public and then resolves to a private address on a second lookup
- **THEN** the connection still goes to the validated address

#### Scenario: Private network opt-in
- **WHEN** allow-private-network is enabled for a destination
- **THEN** private addresses and the `http` scheme are allowed, the address is still pinned, and link-local metadata addresses and `0.0.0.0` are still refused

### Requirement: Google Drive destination
The daemon SHALL upload to Google Drive over HTTPS REST with resumable upload, SHALL list and delete only files it created and recorded, and SHALL NOT use the Google client library. The panel SHALL support OAuth 2.0 with the operator's own client (scope `drive.file`) and a service account JSON key with a shared folder.

#### Scenario: OAuth connect
- **WHEN** an administrator starts "Connect Google Drive" for a destination with a saved client id and secret and completes consent
- **THEN** the panel callback exchanges the code, stores the refresh token as a secret, and shows the destination as connected

#### Scenario: OAuth callback state is verified
- **WHEN** the OAuth callback arrives with a missing, expired, reused, or unknown `state` value, or without an administrator session
- **THEN** the callback is rejected and no token is stored

#### Scenario: Service account folder
- **WHEN** a service account destination is configured with a folder id shared to the service account
- **THEN** uploads, listings, and deletions are restricted to that folder

#### Scenario: Resumable upload recovers a chunk
- **WHEN** a chunk upload fails with a retryable error
- **THEN** the daemon queries the resumable session offset and resumes from it, up to the retry limit

#### Scenario: Chunking and tokens
- **WHEN** a file is uploaded to Drive
- **THEN** chunks are 8 MiB (a multiple of 256 KiB) and access tokens are obtained per job and never persisted

### Requirement: Test connection
The panel SHALL provide an administrator-only test for each destination. The daemon SHALL verify access by writing, reading metadata of, and deleting a small marker object (or, for `local`, writing and removing a marker file and reporting free space), and the test SHALL return a success flag and a sanitized error summary.

#### Scenario: Successful test
- **WHEN** an administrator tests a valid destination
- **THEN** the result reports success and the marker object is removed

#### Scenario: Failed test
- **WHEN** the credentials are invalid
- **THEN** the result reports failure with an error summary that contains no secret

### Requirement: Backup plan model and limits
A backup plan SHALL belong to one instance and define include paths, exclude globs, a preset, an optional schedule, retention from 1 to 100, 1 to 5 destinations, a Minecraft save hook setting, and an enabled flag. Plans SHALL be created, updated, and deleted only by administrators.

#### Scenario: Preset expansion
- **WHEN** an administrator saves a plan with preset `minecraft-worlds`
- **THEN** the stored include list contains `world`, `world_nether`, and `world_the_end`, and the default excludes are applied

#### Scenario: Plan limit
- **WHEN** an administrator creates a fifth plan for an instance that has four
- **THEN** the request is rejected with a limit error

#### Scenario: Retention range
- **WHEN** a plan is saved with retention 0 or 101
- **THEN** the request is rejected with a validation error

#### Scenario: Plan size limits
- **WHEN** a plan has more than 50 include paths, more than 50 exclude globs, or an entry longer than 256 characters
- **THEN** the request is rejected with a validation error

#### Scenario: Preset definitions
- **WHEN** a preset is chosen
- **THEN** `minecraft-worlds` expands to `world`, `world_nether`, `world_the_end`; `minecraft-worlds-plugins-configs` adds `plugins`, `config`, `server.properties`, `ops.json`, `whitelist.json`, `bukkit.yml`, `spigot.yml`; `whole-directory` expands to `.`

### Requirement: Include paths stay inside the instance directory
Every include path SHALL be validated on save and again by the daemon at job start against the instance working directory using the daemon's file-manager path checks. Absolute paths, `..` segments, NUL bytes, and paths resolving outside the working directory SHALL be rejected, and symbolic links SHALL NOT be followed outside it.

#### Scenario: Traversal is rejected
- **WHEN** an administrator saves or a job runs with an include path `../other` or `/etc`
- **THEN** the save is rejected, or the job fails before reading any file, with an illegal-path error

#### Scenario: Symlink escape
- **WHEN** an included directory contains a symbolic link pointing outside the instance working directory
- **THEN** the archive does not contain the linked content

#### Scenario: Missing include path
- **WHEN** an include path does not exist at job time and at least one other include path exists
- **THEN** the missing path is skipped and noted in the record; if no include path exists the job fails

#### Scenario: Exclude matching is bounded
- **WHEN** an exclude glob is pathological
- **THEN** matching completes in bounded time without catastrophic backtracking

### Requirement: Streamed, bounded archiving
The daemon SHALL build the archive as a zip stream written directly to a temporary file in the staging directory and uploaded from that file, SHALL NOT buffer a whole archive in memory, SHALL use a low deflate level (1) and run at most one backup job at a time per daemon with other jobs queued (queue length limit 20, rejecting further jobs), and SHALL abort a job that exceeds the plan timeout (default 6 hours). Temporary files SHALL be removed on success, failure, cancel, and daemon start.

#### Scenario: One job at a time
- **WHEN** three plans fire at the same moment on one daemon
- **THEN** one job runs and two wait in the queue, then run in order

#### Scenario: Queue limit
- **WHEN** 20 jobs are queued and another is requested
- **THEN** the request is rejected with a busy error

#### Scenario: Temp file cleanup
- **WHEN** a job fails halfway
- **THEN** the temporary archive is deleted and no partial object remains at any destination

### Requirement: Disk space precheck
Before archiving, the daemon SHALL estimate the archive size from the total size of the selected files and SHALL refuse the job with a disk-space error when the free space of the staging volume is below the estimate times 1.2. A `local` destination SHALL also refuse a job that would exceed its configured maximum total size after retention.

#### Scenario: Not enough space
- **WHEN** free space is below the estimate times 1.2
- **THEN** the job fails before archiving with a disk-space error and a `backup.failed` event is emitted

### Requirement: Minecraft save consistency
For a plan with the save hook enabled and a running instance, the daemon SHALL send `save-off` and `save-all flush`, wait up to 60 seconds for the save-complete line, archive, and then send `save-on` in a final path that always runs. The hook SHALL default to on for Minecraft instance types.

#### Scenario: Hook runs around the archive
- **WHEN** a plan with the hook enabled runs against a running instance
- **THEN** `save-off` and `save-all flush` are sent before archiving and `save-on` is sent after

#### Scenario: save-on after failure
- **WHEN** archiving fails while the hook is active
- **THEN** `save-on` is still sent

#### Scenario: Stopped instance
- **WHEN** the instance is stopped
- **THEN** no commands are sent and the archive is created

#### Scenario: Save timeout is a warning
- **WHEN** the save-complete line does not arrive within 60 seconds
- **THEN** the backup continues and a warning is recorded

### Requirement: Backup index and per-destination results
The daemon SHALL keep a per-instance index of every backup it created, with id, plan id, time, size, SHA-256, and per-destination status, remote key, and sanitized error, persisted through the storage subsystem and limited to 500 records. A backup SHALL be successful when at least one destination holds a copy.

#### Scenario: Partial failure
- **WHEN** a backup uploads to local successfully and Google Drive fails
- **THEN** the record shows local `ok` and gdrive `failed` with an error summary, and the job is reported as succeeded with a warning

#### Scenario: All destinations fail
- **WHEN** no destination holds a copy
- **THEN** the backup is reported as failed and a `backup.failed` event is emitted

#### Scenario: Index limit
- **WHEN** the index holds 500 records and a new job is requested
- **THEN** the job is refused with a limit error

### Requirement: Retention
After a job produces at least one successful copy, the daemon SHALL apply the plan's retention per destination: keep the newest N `ok` copies of that plan on that destination and delete the rest by recorded id. It SHALL NOT delete the backup created by the current job, SHALL NOT delete objects not in the index, and SHALL NOT select objects by name pattern.

#### Scenario: Keep last N
- **WHEN** a plan with N=3 completes its fifth backup
- **THEN** the two oldest backups are deleted from every destination that holds them and three remain

#### Scenario: Failed destination does not consume retention
- **WHEN** gdrive failed for one of the last three backups
- **THEN** gdrive retention counts only the successful gdrive copies, and local retention counts the local copies

#### Scenario: Unknown files are never touched
- **WHEN** a destination folder contains files that are not in the index
- **THEN** retention leaves them untouched

#### Scenario: New backup is protected
- **WHEN** retention runs immediately after a job
- **THEN** the new backup is never among the deleted

#### Scenario: Failed destination is not pruned
- **WHEN** the current job failed to upload to a destination
- **THEN** retention does not delete anything from that destination

#### Scenario: Deletion failure is retried
- **WHEN** deleting an old copy fails
- **THEN** the job still succeeds and deletion is retried at the next run

### Requirement: Backup now, list, and download
The panel SHALL let an administrator or a user assigned to the instance trigger "Backup now" for any enabled plan of that instance and list its backup records (date, size, per-destination status). Assigned regular users SHALL NOT see destination configuration, secrets, or remote keys. The panel SHALL allow downloading a backup that has a local copy, for administrators and assigned users, through a time-limited single-use download ticket, streaming the file without buffering it.

#### Scenario: Assigned user starts a backup
- **WHEN** a regular user assigned to the instance triggers Backup now for an enabled plan
- **THEN** a job is queued and its record appears in the list

#### Scenario: Unassigned user is refused
- **WHEN** a regular user not assigned to the instance lists backups, triggers a backup, or requests a download
- **THEN** the request is rejected as unauthorized

#### Scenario: Backup-now rate limit
- **WHEN** a regular user triggers Backup now more than once in 60 seconds for the same plan
- **THEN** the extra request is rejected with a rate-limit error

#### Scenario: Remote keys hidden from users
- **WHEN** an assigned regular user lists backups
- **THEN** records contain destination names, types, and statuses but no remote keys, folder ids, or buckets

### Requirement: Restore
Restore SHALL be allowed only to administrators and only while the instance is stopped. The daemon SHALL fetch a remote copy to staging when no local copy exists, verify its SHA-256, validate every archive entry and symlink target against the instance working directory before extracting, and extract only into that directory.

#### Scenario: Running instance refuses restore
- **WHEN** an administrator restores a backup while the instance is running
- **THEN** the request is rejected with an instance-must-be-stopped error

#### Scenario: Regular user cannot restore
- **WHEN** a regular user assigned to the instance requests a restore
- **THEN** the request is rejected as forbidden

#### Scenario: Malicious archive
- **WHEN** a restore archive contains an entry named `../../etc/cron.d/x` or a symlink pointing outside the instance directory
- **THEN** the restore is refused before any file is written and the instance files are unchanged

#### Scenario: Rollback on failure
- **WHEN** extraction fails halfway
- **THEN** the previous files of the restored paths are put back

#### Scenario: Previous files are kept until success
- **WHEN** a restore starts
- **THEN** existing files of the restored paths are moved to a rollback directory and removed only after successful extraction

### Requirement: Backup events for notifications
On every finished job the panel SHALL publish exactly one event, `backup.succeeded` or `backup.failed`, to the in-process event bus, with the payload defined in the design contract (event, occurredAt, instance, plan, backup id, trigger, size, duration, destination results, warnings, error summary). Payloads SHALL contain no secrets, remote keys, or file paths outside the instance-relative include list. A job with at least one successful copy SHALL publish `backup.succeeded`.

#### Scenario: Success event
- **WHEN** a scheduled job succeeds on all destinations
- **THEN** one `backup.succeeded` event is published with per-destination results

#### Scenario: Failure event
- **WHEN** a job fails on every destination
- **THEN** one `backup.failed` event is published with a sanitized error summary

### Requirement: Panel-daemon credential delivery
The panel SHALL send destination configuration and decrypted secrets to the daemon only inside the authenticated panel-daemon request for a job, and the daemon SHALL keep them in memory only for that job. Scheduled jobs SHALL obtain credentials through a daemon-to-panel trigger.

#### Scenario: Secrets are not persisted by the daemon
- **WHEN** a job finishes
- **THEN** no daemon data file or log contains the destination secret

#### Scenario: Panel unreachable at schedule time
- **WHEN** a scheduled job starts while the panel cannot be reached
- **THEN** the job fails with a recorded error and a failure is reported when the panel reconnects

#### Scenario: Scheduled job obtains credentials
- **WHEN** a scheduled `backup` action fires
- **THEN** the daemon notifies the panel, which replies with a job request carrying the credentials

### Requirement: Failure handling and timeouts
Each destination upload SHALL be retried up to 3 times with exponential backoff for retryable errors (network errors, HTTP 5xx, HTTP 429), SHALL have a per-request timeout of 60 seconds, and SHALL have an overall job timeout. A job SHALL be cancellable by an administrator while queued or running. Cancel SHALL stop archiving, abort uploads, run the `save-on` path, and remove temporary files and partial remote objects.

#### Scenario: Retry then fail
- **WHEN** an upload fails with HTTP 503 four times
- **THEN** it is retried three times and then recorded as failed for that destination

#### Scenario: Cancel
- **WHEN** an administrator cancels a running job
- **THEN** the job stops, `save-on` is sent if needed, and no temporary file or partial object remains

### Requirement: Localized user-facing text
All backup UI text and panel error messages SHALL use i18n keys defined in `en_US.json`, `zh_CN.json`, and `tr_TR.json`.

#### Scenario: Turkish locale
- **WHEN** a user with the Turkish locale opens the Backups page
- **THEN** labels, statuses, and errors are shown in Turkish
